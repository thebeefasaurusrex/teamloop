## Claude failure audit and file-only recovery

The installed Claude Code CLI 2.1.310 could hit a response output limit with thinking-only content, filter a standalone incomplete thinking block during request normalization, then ask the model to resume the missing thought. Source-and-trace inspection found 20 qualifying transitions across eight captured non-delivery streams. Two older buffered timeouts lacked enough evidence to name their internal cause.

This is not an absolute block on structured completion: successful controls used the same completion contract. Thinking sharing a message with a tool call can survive normalization. The evidence does not establish why the first response spent its budget thinking, and it is not a direct capture of outgoing HTTP bodies. The original large-build results remain evidence about the observed CLI route, with underlying-model ability claims qualified.

A small baseline diagnostic reproduced four thinking-only responses, three continuation nudges and no deliverable. Explicit recovery guidance returned valid JSON with an unknown answer, not a demonstrated task recovery. No verified native fix or remove-the-cap switch was established. The per-response output ceiling was already 128,000 tokens including thinking. Durable files preserve progress; that does not prove the native continuation behavior fixed.

The existing public correction in `src/team-loop.mjs` preserves recognized Claude terminal output-limit errors instead of flattening them into a generic worker exit. That diagnostic improvement was already published. It does not repair the native continuation behavior or prove a failed benchmark recovered.

The precision case was source-review-triggered, then applied identically to both apps; it was a declared supplement rather than an originally enumerated fixture. One nine-second 6.1 invocation was interrupted by a watchdog misreading permission prose in a successful Read as an error. Scores were locked by a masked reviewer before identity joining. Haiku's startup failure remains unrepaired.

Haiku did not earn automatic feature-owner promotion: one critical startup failure, and a useful comparison app eight points behind 6.1, outside the predeclared five-point tolerance, with a known data-fidelity defect. Active lead minutes were not directly measured, so no 25% labor-saving claim is justified. Earlier Haiku design strengths remain evidence, but do not establish a dependable calculator specialty. Reporting categories differ between providers.

Subscription headroom was checked around calls. Claude usage credits and auto-reload remained off; no paid API fallback, paid overflow or silent provider substitution was used. Rounded account-wide meters include unrelated activity and do not establish per-model allowance cost. No dollar, percentage-saving or lead-labor conversion is justified.
